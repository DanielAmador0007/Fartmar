# Despliegue y operación

**Arranque:** `cp .env.example .env && docker compose up -d --build --wait` (`make up`) → http://localhost:8080. Orden: `db` → `migrate` (one-shot: migraciones, rol de la app, semilla demo) → `api` (PHP-FPM) y `scheduler` → `web` (Nginx: SPA + FastCGI de `/api`, `/health`, `/ready`). Migrar aparte evita que varias réplicas compitan y que la API arranque con el esquema a medias. Redes: `edge` (web, api) y `data` (api, migrate, scheduler, db): Nginx no llega a Postgres. Desarrollo: `make dev` (S-99). Imágenes sin root, `cap_drop: ALL`, sin `tests/`, `APP_DEBUG=false` fijo.

**Secretos** (gestor de secretos, nunca el repo): `APP_KEY`, `PATIENT_HASH_KEY`, `POSTGRES_PASSWORD`, `DB_APP_PASSWORD`, `LLM_API_KEY` (solo llega a `api`). Generar: `openssl rand -base64 32` (con prefijo `base64:`). Demo: `ALLOW_GENERATED_KEYS=true` genera las llaves una vez en el volumen `app_keys`; producción: `false` y `SEED_DEMO_DATA=false` (`deploy.sh production` aborta si no). **Respalde `APP_KEY` y `PATIENT_HASH_KEY` aparte de la BD** (en el gestor de secretos): sin ellas un respaldo restaurado no permite leer ni buscar documentos de pacientes.

**BD: dueño ≠ aplicación.** `migrate` usa el dueño; `api`/`scheduler`, `fartmar_app` (`db:provision-app-role`): sin `TRUNCATE` ni DDL; kardex y bitácoras solo `SELECT`/`INSERT`. Por defecto el comando crea el rol y le fija la clave en cada despliegue, lo que exige superusuario o `CREATEROLE`. Con un PostgreSQL gestionado: el DBA crea el rol (`CREATE ROLE fartmar_app LOGIN PASSWORD '…'`) y se pone `DB_APP_ROLE_MANAGED_EXTERNALLY=true`: `migrate` solo aplica `GRANT`/`REVOKE` y falla claro si el rol no existe. Si una sentencia falla, el error no incluye el SQL (lleva la clave).

## Estrategia (`.github/workflows/ci.yml`)
Lint + auditorías (`composer audit`, `npm audit`) → pruebas (Pest con PostgreSQL 16 y concurrencia, Vitest, `assistant:eval`) → **imágenes inmutables** + Trivy (HIGH/CRITICAL con arreglo) → **staging** en el runner (smoke con escrituras demo como `fartmar_app`, no-root, `TRUNCATE` denegado, respaldo + restauración) → **publicación en GHCR** (`sha` + `latest`, solo `main`) → **producción**. Acciones fijadas por SHA.

**Aprobación de producción (el repo es público, hay que configurarla):** 1) *Settings → Environments → New environment* `production` → *Required reviewers* (Daniel) y, opcional, *Deployment branches: main*; ahí mismo los secretos `SMOKE_EMAIL`/`SMOKE_PASSWORD` (usuario de solo lectura para el smoke en producción). 2) *Settings → Secrets and variables → Actions → Variables* → `PRODUCTION_REVIEWERS_CONFIGURED = true`. Sin esa variable un push a `main` **no** despliega; solo una ejecución manual (*Actions → CI → Run workflow* en `main`) con `confirm_production=DESPLEGAR`. Los despliegues son simulados (`scripts/deploy.sh`, `DRY_RUN=1`): respaldo → pull del SHA → `migrate` → `up --wait` → smoke. Un solo host = segundos de corte; en un orquestador, *rolling update* o blue/green con `/ready` (readiness) y `/health` (liveness).

## Migraciones y rollback
**Expand/contract:** cada versión solo agrega (columnas nulas o con default, tablas, índices `CONCURRENTLY`) y convive con el esquema anterior; borrar o renombrar va después (*contract*). **Rollback** = desplegar el SHA anterior (`DRY_RUN=0 scripts/deploy.sh production <api:sha> <web:sha>`), nunca `migrate:rollback`; si el daño es de datos, restaurar el respaldo previo. Interruptores por configuración (p. ej. `LLM_PROVIDER=mock`).

## Respaldo y restauración
- `scripts/backup.sh` (`.\make.ps1 backup`): `pg_dump -Fc` en el contenedor, control con `pg_restore --list`, `.sha256`, archivos `umask 077`, retención `RETENTION_DAYS=14`. Cron cada 6 h (`0 */6 * * * cd /srv/fartmar && scripts/backup.sh /backups`) y copia fuera del host (cifrada, versionada).
- **Prueba de restauración** (semanal y en CI): `scripts/restore.sh <archivo>` (`.\make.ps1 restore <archivo>`): BD temporal, verifica migraciones, conteos y kardex = existencias; la BD temporal se borra siempre (trap).
- **Restauración real:** `scripts/restore.sh <archivo> --into-live` (pide el nombre de la BD; usa el compose del entorno en ejecución o `COMPOSE=…`): detiene la app, reemplaza la BD y levanta el stack.
- **RPO ≤ 6 h** con dumps (≤ 5 min con WAL/PITR, p. ej. pgBackRest); **RTO ≤ 1 h**.

## HTTPS, proxies y red
La demo publica HTTP en 8080. En producción TLS termina en Nginx o en un balanceador: activar HSTS (comentado en `docker/nginx/fartmar/security-headers.conf`, empezar con `max-age` corto). **Limitaciones detrás de un balanceador:** Nginx reescribe `X-Forwarded-For` y `X-Forwarded-Proto` con lo que él ve (`$remote_addr`, `$scheme`), y Laravel no confía en proxies (`TRUSTED_PROXIES` vacío). Con TLS en el balanceador, Laravel vería `http` y la IP del balanceador hasta configurar en Nginx `set_real_ip_from` (comentado en `docker/nginx/default.conf`) y pasar el esquema original (p. ej. `map $http_x_forwarded_proto` solo desde la red del balanceador); `TRUSTED_PROXIES` sirve solo si PHP queda detrás de un proxy HTTP, no de FastCGI. En Docker Desktop toda petición llega con la IP del gateway de Docker (p. ej. `172.x.0.1`): la IP real del cliente solo se ve en Linux o detrás de un balanceador configurado. Postgres solo en `127.0.0.1`.

## Observabilidad
`/health` (sin BD) y `/ready` (BD + migraciones), sin autenticación. Logs JSON: Laravel (`correlation_id`, PII redactada) y el **access log de Nginx**, que registra la ruta sin query string, sin cuerpos ni `Authorization`; se cruzan por `request_id` = `client_correlation_id`. Rotación `json-file` 10 MB × 3.
