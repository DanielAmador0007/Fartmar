# Supuestos

Decisiones tomadas ante ambigüedades del enunciado (sección 8: "toma una decisión razonable y regístrala"). Se irán ampliando en cada fase.

## Entorno e infraestructura

| # | Supuesto | Motivo |
|---|---|---|
| S-01 | Base de datos **PostgreSQL 16**. | `SELECT … FOR UPDATE`, CHECK constraints, triggers e índices parciales defienden las reglas de negocio en la BD (RN-03, RN-06, RN-08). |
| S-02 | Las pruebas automáticas corren **contra PostgreSQL** (BD `fartmar_test`), nunca contra SQLite. | Las restricciones y el bloqueo de filas son justamente lo que se prueba; SQLite no los reproduce igual. |
| S-03 | PHP 8.4 y Laravel 13 (última estable al crear el proyecto). | El enunciado pide PHP ≥ 8.2 y la versión estable vigente. |
| S-04 | No se requiere PHP en el host: Composer, Artisan, Pint, Larastan y Pest se ejecutan dentro del contenedor `api`. | Reproducibilidad y un solo prerrequisito (Docker). Node se usa en el host para el frontend en desarrollo. |
| S-05 | En desarrollo, la API usa el servidor embebido de PHP con 4 workers; producción usará php-fpm + Nginx (fase DevOps). | Simplicidad en Fase 0; la imagen de producción es multi-stage y no root. |
| S-06 | Puertos del host: Postgres 55432, API 8080, frontend 5173. | Evitar conflictos con otros servicios locales (5432/5433 suelen estar ocupados). |
| S-07 | `APP_KEY` se genera en el entrypoint si falta, **solo para la demo**. En un entorno real se inyecta como secreto y nunca se regenera (invalidaría datos cifrados, p. ej. documentos de pacientes). | Levantar todo con un solo comando sin commitear secretos. |
| S-08 | La clave de Postgres en `.env.example` (`fartmar_local_demo`) es un valor de demo local, no un secreto. | Permite `cp .env.example .env && docker compose up` sin pasos manuales. |

| # | Supuesto | Motivo |
|---|---|---|
| S-09 | `GET /health` = liveness: responde 200 si el proceso PHP atiende; **no consulta la BD**. | Una caída de la BD no debe provocar reinicios en cascada de la API. |
| S-10 | `GET /ready` = readiness: 200 solo si la BD responde **y** no hay migraciones pendientes; si no, 503. | Evita enrutar tráfico a una instancia con esquema desactualizado. |

## Modelo de datos (Fase 1)

| # | Supuesto | Motivo |
|---|---|---|
| S-16 | `stocks.product_id` está **denormalizado** (se puede derivar del lote) y una FK compuesta `(lot_id, product_id) → lots(id, product_id)` impide que sea inconsistente. El mismo patrón se usa en kardex, dispensaciones y traslados. | Consultar y bloquear existencias por bodega + producto (FEFO, alertas de mínimo) sin join, sin riesgo de que el producto no coincida con el lote. |
| S-17 | El número de documento del paciente se guarda **cifrado** (cast `encrypted`, AES-256 con `APP_KEY`) y además `document_hash = HMAC-SHA256("TIPO:NÚMERO")` con `PATIENT_HASH_KEY` (o `APP_KEY` si no se define). El número se normaliza (sin puntos, guiones ni espacios). | El cifrado no permite buscar ni garantizar unicidad; el HMAC sí. Se usa HMAC y no SHA-256 simple porque los documentos tienen pocos valores posibles y un hash sin clave se revierte por fuerza bruta. |
| S-18 | El teléfono del paciente también se cifra; nombres y fecha de nacimiento quedan en claro (se necesitan para buscar y mostrar, y se enmascaran en la API según el rol). | Equilibrio entre privacidad y usabilidad. |
| S-19 | La dispensación se modela en tres niveles: `dispensations` (cabecera) → `dispensation_items` (línea de prescripción y cantidad) → `dispensation_item_lots` (lotes FEFO). | Una dispensación de control especial queda `PENDIENTE_AUTORIZACION` con sus líneas pero **sin lotes**; los lotes y la salida de stock se asignan al autorizar (CLAUDE.md §6.4). |
| S-20 | El traslado sigue el mismo patrón: `transfer_items` (producto y cantidad solicitada) → `transfer_item_lots` (lotes despachados y recibidos). Los lotes se eligen **al despachar** (FEFO, sin vencidos). Una discrepancia por lote despachado. | Entre la solicitud y el despacho el stock cambia; asignar lotes al despachar evita reservar lotes que luego se vencen o se agotan. |
| S-21 | Una prescripción es **vigente** si `status = 'ACTIVA'` y `valid_until >= hoy` (zona de negocio). Estados: `ACTIVA`, `COMPLETADA`, `ANULADA`. Un producto aparece una sola vez por prescripción. | El enunciado no define estados de prescripción. |
| S-22 | Quien **autoriza o rechaza** un controlado y quien **aprueba** un traslado debe tener rol `regente_farmacia`; lo verifica un trigger además de la Policy. | Defensa en profundidad de RN-05 y de la tabla de roles. |
| S-23 | Las tablas append-only (kardex, bitácoras) bloquean UPDATE/DELETE por trigger, pero **no TRUNCATE ni DROP** (los usan las pruebas y `migrate:fresh`). En producción la app debe conectarse con un usuario de BD que no sea dueño de las tablas. | Se documenta como riesgo residual. |
| S-24 | `idempotency_key` es UNIQUE **global** (no por usuario). El cliente debe generar un UUID por intento lógico. | Simplicidad; una colisión de UUID entre usuarios es despreciable y, si ocurre, el `request_hash` distinto devuelve 409. |
| S-25 | Las columnas polimórficas (`kardex_movements.reference_type`, `audit_logs.auditable_type`) guardan alias cortos (`dispensation`, `transfer`, …) vía `Relation::enforceMorphMap`. | Renombrar una clase PHP no rompe datos históricos inmutables. |
| S-26 | Datos semilla: vencimientos **relativos a hoy**; re-ejecutar el seeder recalcula fechas de lotes y la vigencia de las prescripciones, pero **no modifica existencias ya creadas** (el kardex es inmutable). Usuarios de demo con contraseña `password` (ver `docs/modelo-datos.md`). | La demo siempre muestra lote vencido, por vencer (< 30 días) y en ventana de alerta, sin importar cuándo se levante. |

## Dispensación y API (Fase 2)

| # | Supuesto | Motivo |
|---|---|---|
| S-27 | La API de negocio vive bajo **`/api/v1/*`** (precisa S-12). | Versionar desde el inicio permite cambios incompatibles sin romper el frontend. |
| S-28 | `request_hash` = SHA-256 de **usuario + payload canónico** (líneas ordenadas por `prescription_item_id`). La misma `Idempotency-Key` enviada por otro usuario es un conflicto (409). | Un reintento legítimo siempre lo hace el mismo usuario; así nadie obtiene la dispensación de otro adivinando su clave. |
| S-29 | Crear responde **201**; un reintento idéntico responde **200** con `Idempotent-Replayed: true` y la misma dispensación (en su estado actual, ver S-46). Sin header `Idempotency-Key` → 422 `VALIDACION` (formato: 8–100 caracteres `[A-Za-z0-9_-]`, se recomienda UUID). *(Actualizado en la revisión de la Fase 2: antes también aceptaba `:` y `.`, y el mensaje de error pedía "un UUID" aunque la regla aceptaba más.)* | Distinguir creación de repetición sin que el cliente tenga que comparar cuerpos. |
| S-30 | Si **cualquier** línea de una dispensación es de control especial, **toda** la dispensación queda `PENDIENTE_AUTORIZACION` y nada sale hasta que se autorice. | Una dispensación es una unidad (una entrega). El frontend puede separar controlados y no controlados en dos solicitudes si se quiere entregar lo demás de inmediato. |
| S-31 | Una dispensación pendiente **reserva cantidad de la prescripción** (no se puede pedir de nuevo lo que ya está esperando autorización) pero **no reserva stock**: al autorizar se vuelven a validar vigencia, saldo y existencias, y puede fallar con `STOCK_INSUFICIENTE`. Rechazar libera la reserva. | Reservar stock exigiría otra tabla y liberar reservas vencidas; validar al autorizar es más simple y nunca deja stock negativo. |
| S-32 | En controlados, el movimiento de kardex queda a nombre del **regente que autoriza** (es quien ejecuta la salida); quien la creó queda en `dispensations.created_by`. | Trazabilidad: ambos usuarios quedan registrados. |
| S-33 | Cuando todas las líneas de una prescripción quedan entregadas, la prescripción pasa automáticamente a `COMPLETADA`. | S-21 define COMPLETADA como "todo dispensado". |
| S-34 | La vista previa FEFO (`GET /dispensations/preview`) es por producto + bodega + cantidad, **no bloquea filas** y es orientativa: la asignación real se hace al confirmar, con bloqueo. | Mostrar lotes antes de confirmar sin retener existencias de otros usuarios. |
| S-35 | RN-01 (nunca un lote vencido) aplica a `SALIDA_DISPENSACION` y `SALIDA_TRASLADO`. Un `AJUSTE` negativo **sí** puede retirar un lote vencido (baja por vencimiento, con motivo). | Sin esa excepción, el stock vencido no podría darse de baja nunca. |
| S-36 | Login: mismo mensaje si el correo no existe, la clave es incorrecta o el usuario está inactivo; límite de **5 intentos por minuto por correo + IP** y **20 por minuto por IP** (429 con `Retry-After`). Los tokens vencen a los `SANCTUM_EXPIRATION` minutos (**480**, un turno) contados desde el login, sin renovación por uso; `sanctum:prune-expired` los borra a diario. *(Actualizado en la revisión de seguridad de la Fase 2; antes: 10/min por IP y sin expiración.)* | No revelar qué correos existen; frenar fuerza bruta sobre una cuenta y barridos desde una IP; limitar el daño de un token filtrado. |
| S-37 | Las Policies exigen además que el usuario esté **activo** (`is_active`). | Un usuario desactivado con un token antiguo no debe poder autorizar ni dispensar. |
| S-38 | Si una dispensación **falla** (stock insuficiente, prescripción excedida…), su `Idempotency-Key` no queda registrada (la transacción se deshace): un reintento con la misma clave se procesa como nuevo. | El cliente puede reintentar con la misma clave cuando se corrige la causa (p. ej. llega stock) sin generar una clave nueva; nunca hay doble salida porque el fallo no movió nada. |
| S-39 | Pedir sobre una prescripción `COMPLETADA` responde `PRESCRIPCION_NO_VIGENTE` (422), no `PRESCRIPCION_EXCEDIDA`: primero se valida el estado de la prescripción y después el saldo de cada línea. | El estado explica mejor la causa ("ya se entregó todo") que el saldo en cero. |

## Seguridad (revisión de la Fase 2)

| # | Supuesto | Motivo |
|---|---|---|
| S-40 | La API autentica **solo con token Bearer** de Sanctum (`sanctum.guard = []`), no con cookie de sesión (modo SPA descartado). El frontend guarda el token en memoria/`sessionStorage` y lo envía en `Authorization`. | Sin cookies no hay superficie CSRF y el mismo mecanismo sirve para el SPA, pruebas y clientes externos. El costo (un XSS podría leer el token) se mitiga con expiración corta y CSP en Nginx (Fase 7). |
| S-41 | Un usuario **desactivado deja de autenticar** de inmediato aunque tenga un token vigente (401 en todo, incluido `/auth/me`), además de perder permisos en las Policies (S-37). | Desactivar a alguien debe cortar el acceso sin esperar a que venza el token. |
| S-42 | `GET /dispensations/{id}`: cualquier auxiliar, regente o auditor activo puede ver **cualquier** dispensación (de cualquier bodega). No hay asignación usuario ↔ bodega en el modelo. La respuesta solo trae `patient_id`, nunca nombre ni documento. | El enunciado no define bodegas por usuario; la exposición de datos personales es nula en este endpoint. Si se agrega asignación por bodega, se restringe en `DispensationPolicy::view`. |
| S-43 | Los ids de ruta aceptan de 1 a 18 dígitos sin ceros a la izquierda; lo demás responde 404. Lo mismo para el id del token Bearer (`id|secreto`), que responde 401. | Un id fuera del rango de `bigint` llegaba a PostgreSQL y respondía 500 (con `APP_DEBUG=true`, con el SQL y el host en el cuerpo). |
| S-44 | Con `APP_DEBUG=false`, cualquier error inesperado en `/api/*` responde `500 ERROR_INTERNO` sin detalles; con `APP_DEBUG=true` (solo desarrollo) se deja el detalle de Laravel. | No filtrar SQL, rutas ni datos de conexión en producción sin perder la depuración en local. |
| S-45 | CORS: solo los orígenes de `CORS_ALLOWED_ORIGINS` (por defecto `http://localhost:5173`), sin credenciales, con los headers que usa la API (`Authorization`, `Idempotency-Key`, `X-Correlation-Id`) y exponiendo `Idempotent-Replayed` y `Retry-After`. | El valor por defecto de Laravel permite cualquier origen (`*`). |

## Revisión de la Fase 2 (dominio)

| # | Supuesto | Motivo |
|---|---|---|
| S-46 | **Semántica del reintento idempotente:** un `POST /dispensations` con una `Idempotency-Key` ya usada (mismo usuario y mismo contenido) responde **200** (no 201) con el header `Idempotent-Replayed: true` y el **estado actual** de la dispensación, no una copia guardada de la primera respuesta. Ejemplo: un controlado creado `PENDIENTE_AUTORIZACION` y luego autorizado se ve `COMPLETADA` en el reintento. No se guarda el cuerpo original. | (1) Lo que garantiza RN-09 es **"sin efecto duplicado"** (una sola dispensación, una sola salida de stock), y eso se cumple siempre. (2) 200 + header le dice al cliente que no se creó nada nuevo sin obligarlo a comparar cuerpos; 201 sería falso porque no se creó un recurso. (3) Devolver el estado actual es más útil y seguro que un snapshot: el auxiliar no actúa sobre un estado viejo (p. ej. volver a pedir autorización de algo ya autorizado). (4) Evita guardar respuestas completas (más almacenamiento y más copias de datos). Costo aceptado: el cuerpo del reintento puede diferir del primero; el cliente debe leer `status` y no asumir que es idéntico. |
| S-47 | Todo `/api/v1` autenticado tiene un límite de **120 solicitudes por minuto por usuario** (`API_RATE_LIMIT_PER_MINUTE`); al superarlo, 429 `DEMASIADAS_SOLICITUDES` con `Retry-After`. Se cuenta por usuario (el middleware corre después de `auth:sanctum`), no por IP, porque en una IPS varios equipos pueden salir por la misma IP. | Frenar scripts o clientes en bucle (incluido el reintento automático de dispensaciones) sin afectar el uso normal de un auxiliar, que no supera unas pocas solicitudes por minuto. |

## Traslados, ajustes, alertas y kardex (Fase 3)

| # | Supuesto | Motivo |
|---|---|---|
| S-48 | Un lote que **venció mientras viajaba** sí se recibe en la bodega destino (`ENTRADA_TRASLADO`). RN-01 impide dispensarlo o volver a trasladarlo; se da de baja con un `AJUSTE` negativo (S-35) y aparece en las alertas como vencido (S-51). | La recepción registra la existencia física: si se rechazara, las unidades quedarían "en el aire" (ni en origen ni en destino) y el kardex no cuadraría con lo que hay en el estante. |
| S-49 | `requested_by` es quien **crea** el borrador, y solo esa persona lo **solicita** (`submit`). Policy + `TransferService` (403 `NO_AUTORIZADO` / `SEGREGACION_FUNCIONES` con `reason = NO_ES_SOLICITANTE`). | Así el "solicitante" de RN-08 es una sola persona; si cualquiera pudiera enviar el borrador de otro, un regente podría hacer que un tercero "solicite" y luego aprobar él mismo. |
| S-50 | Una discrepancia `PENDIENTE` la resuelve **un regente distinto de quien recibió el traslado** (S-60; Policy de rol, servicio y triggers de BD), **una sola vez** (una vez `RESUELTA` la BD no deja cambiarla), con texto obligatorio y una acción: **`REINTEGRAR_ORIGEN`** (las unidades nunca salieron: `AJUSTE` +faltante en la bodega **origen**, con motivo que cita la discrepancia y el traslado, `reference` = la discrepancia) o **`PERDIDA`** (se perdieron o dañaron en el camino: solo se registra, sin mover stock, porque ya salieron del origen con `SALIDA_TRASLADO`). El traslado sigue `RECIBIDO_PARCIAL` (estado final) aunque todas sus discrepancias se resuelvan. Columna `resolution_action` con CHECK (nueva migración). | Son los dos desenlaces físicos posibles. Reingresar al destino no se ofrece: si llegaron, se debieron registrar al recibir. Mantener `RECIBIDO_PARCIAL` conserva la historia de que hubo faltante; el estado de cada discrepancia dice si está cerrada. |
| S-51 | **Alertas** (`GET /alerts`): (1) vencimiento = existencias con unidades (> 0) cuyo lote vence en **≤ `ALERT_EXPIRY_DAYS`** días desde hoy (Bogotá), **incluidos los ya vencidos** (`is_expired: true`, `days_to_expire` negativo), ordenadas por vencimiento; (2) stock mínimo = por bodega + producto **con mínimo definido**, cuando lo **disponible en lotes no vencidos** es **menor** (estricto) que `min_quantity`; incluye productos con mínimo y sin ninguna existencia. Un mínimo de 0 nunca alerta. | Un lote vencido con unidades es la alerta más urgente (hay que darlo de baja). Para el mínimo se cuenta solo lo que se puede usar: un lote vencido no cubre la demanda. "Bajo el mínimo" se interpreta literalmente (estar en el mínimo no alerta). |
| S-52 | **Despachar y recibir** lo pueden hacer auxiliar o regente activos; no se exige que sean distintos del solicitante ni del aprobador. Tampoco hay asignación usuario ↔ bodega (igual que S-42): cualquier personal de farmacia puede despachar o recibir cualquier traslado. | La segregación que exige el enunciado es solicitar ≠ aprobar (RN-08). Restringir por bodega requiere un modelo de asignación que el enunciado no define; si se agrega, se restringe en `TransferPolicy`. |
| S-53 | **Anular** lo puede hacer quien creó el traslado o cualquier regente, solo desde `BORRADOR`, `SOLICITADO` o `APROBADO`, con motivo (5–500 caracteres; CHECK `transfers_cancel_reason_required` en BD). | Antes de despachar no se ha movido stock, así que anular no requiere compensaciones. Un auxiliar no debe poder anular el traslado que pidió otra persona. |
| S-54 | **El despacho es todo o nada**: si algún producto no tiene suficientes unidades **no vencidas** en el origen, responde 409 `STOCK_INSUFICIENTE` (con producto, pedido y disponible), no sale nada de ningún producto y el traslado sigue `APROBADO`. No hay despachos parciales: para enviar menos, se anula y se crea otro traslado. | Un despacho parcial obligaría a definir "pendiente por despachar" y más estados. Así la cantidad despachada siempre es la aprobada. |
| S-55 | **La recepción es una sola**: el cuerpo debe traer **todos** los lotes despachados (`transfer_item_lot_id`) con la cantidad recibida de cada uno (0..despachado; 0 si no llegó nada). Faltan lotes, sobran o la cantidad está fuera de rango → 422 `TRASLADO_INVALIDO` sin cambios. Lo que falte queda como discrepancia por lote. | Recepciones sucesivas complicarían el estado (¿cuándo se cierra?). Exigir todos los lotes evita que un olvido se convierta en "no llegó". |
| S-56 | **Ajustes** (`POST /inventory-adjustments`): solo regente activo; `quantity` con signo (positivo suma, negativo resta, nunca 0); motivo de 5–500 caracteres; un ajuste positivo puede crear la existencia de un lote en una bodega que no lo tenía y **sí se permite sobre un lote vencido** (sobrante de conteo, o `REINTEGRAR_ORIGEN` de un lote que venció en tránsito): registrar unidades que existen físicamente no es dispensar ni trasladar, RN-01 las sigue excluyendo de FEFO y aparecen en alertas como vencidas para darlas de baja; uno negativo puede retirar un lote vencido (S-35) pero nunca deja stock negativo (409). No hay tabla de ajustes: el movimiento `AJUSTE` del kardex **es** el registro (sin `reference`), y `audit_logs` guarda el ajuste con IDs y cantidades (sin el motivo, que es texto libre). | Evita duplicar datos; el kardex ya es inmutable y tiene usuario, motivo, cantidad y saldo. |
| S-57 | **Kardex** (`GET /kardex`): del más reciente al más antiguo (`created_at`, luego `id`); filtros `warehouse_id`, `product_id`, `lot_id`, `type`, `from`, `to` y documento de origen `reference_type` (`dispensation`, `transfer`, `transfer_discrepancy`, alias del morph map) + `reference_id` (exige el tipo). `from`/`to` (`YYYY-MM-DD`) son días completos en hora de Bogotá (S-13) convertidos a UTC; `to` incluye todo ese día. Página de hasta 100 (50 por defecto). Lo consultan auxiliar, regente y auditor. | El usuario piensa en días locales; las fechas se guardan en UTC. |
| S-58 | Las **observaciones** (`notes`) de un traslado y los textos de anulación y de resolución son texto libre **no confiable**: solo se valida la longitud (`notes` ≤ 1000) y se devuelven tal cual como datos; nunca se interpretan ni se registran en `audit_logs`. | La Fase 6 (asistente IA) los tratará como datos delimitados para evitar inyección de instrucciones; el frontend los escapa al mostrarlos. |
| S-59 | Un traslado de un medicamento de **control especial** no requiere autorización adicional: RN-05 aplica a la **dispensación** al paciente. El traslado ya exige aprobación de un regente distinto del solicitante (RN-08). | El enunciado limita la doble autorización a la dispensación; el traslado tiene su propia segregación. |

## Revisión de la Fase 3

| # | Supuesto | Motivo |
|---|---|---|
| S-60 | **Quien recibió un traslado no resuelve sus discrepancias** (M5): `TransferService` responde 403 `SEGREGACION_FUNCIONES` (`details.reason = ES_RECEPTOR`) y el trigger `transfer_discrepancies_check_resolver` lo vuelve a exigir. No se exige que sea distinto de quien despachó, aprobó o solicitó. | Quien declara el faltante al recibir no debe ser quien decide si "volvió al origen" o "se perdió": un mismo regente podría inventar un faltante y cerrarlo sin revisión. Es la misma idea de RN-08. Se limita al receptor porque es quien produce el dato que se resuelve. |
| S-61 | **Los ajustes de inventario no son idempotentes** (M4): `POST /inventory-adjustments` no exige `Idempotency-Key`; un doble envío crea dos movimientos `AJUSTE`. Se mitiga en el frontend (botón deshabilitado mientras la solicitud está en curso, Fase 5) y se corrige con un ajuste en sentido contrario (el kardex es inmutable). Mejora futura: reutilizar el mecanismo de RN-09 (clave + hash del cuerpo). | El ajuste es una operación manual, poco frecuente y solo de regente; RN-09 exige idempotencia para la dispensación, que es la operación masiva con reintentos automáticos. Se prioriza el núcleo evaluado. |
| S-62 | **`GET /alerts` devuelve como máximo `limit` filas por lista** (100 por defecto, máximo 500), las más urgentes primero (vencimiento más próximo; bodega + producto en stock mínimo), y `expiring_lots_total` / `low_stock_total` con el total real. Sin paginación por páginas. | Las alertas son un tablero: lo útil es lo más urgente y saber si hay más. Un límite evita respuestas enormes en una red grande; si el total supera el límite, se filtra por bodega. |
| S-63 | **Stock en tránsito** (`GET /stocks/in-transit`, M1) = lotes despachados de traslados `EN_TRANSITO` sin recepción registrada (`quantity_received IS NULL`).
